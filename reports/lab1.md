# Lab1：多道程序与分时多任务

## 1. 实验要求

本实验对应 rCore 第三章。在已有多任务内核上，实现任务追踪系统调用 `sys_trace`，使用户程序能够读取或修改指定地址处的一个字节，并查询当前任务的系统调用次数。实验同时要求时间查询、主动让出 CPU 和定时中断驱动的任务切换能够正常工作。

第三章内核将多个用户程序装入不同的内存区域，通过任务控制块保存任务状态和上下文。用户程序执行 `ecall` 后进入内核，由统一入口分发系统调用。在这一基础上，追踪功能需要为每个任务增加独立的统计数据，并将统计过程接入系统调用入口。

### 1.1 系统调用接口

`sys_trace` 的系统调用编号为 `410`，函数接口如下：

```rust
pub fn sys_trace(trace_request: usize, id: usize, data: usize) -> isize
```

三个参数的含义由 `trace_request` 决定：

| 请求值 | `id` 的含义 | 操作 | 返回值 |
| --- | --- | --- | --- |
| `0` | 待读取的字节地址 | 读取该地址处的一个无符号字节，忽略 `data` | 字节值，范围为 `0` 至 `255` |
| `1` | 待写入的字节地址 | 将 `data` 转换为 `u8` 后写入该地址 | `0` |
| `2` | 系统调用编号 | 查询当前任务调用该系统调用的次数 | 调用次数 |
| 其他值 | 忽略 | 拒绝该请求 | `-1` |

请求 `2` 有两项关键要求：统计对象是当前任务；发起查询的本次 `sys_trace` 调用也计入统计。例如，当前任务第一次查询 `410` 的调用次数时，若此前没有执行过 `sys_trace`，结果应为 `1`。

### 1.2 需要补充的内容

本次实现主要增加以下内容：

1. 在任务控制块中保存按系统调用编号索引的计数数组。
2. 在任务管理模块中提供当前任务计数的更新和查询接口。
3. 在系统调用统一入口中记录调用次数。
4. 在 `sys_trace` 中实现字节读写、计数查询和非法请求处理。

仓库中的 `sys_get_time`、任务上下文切换和调度器已经具备基础实现。本次保留这些机制，并通过第三章测例验证它们与新增追踪功能的协同运行。

## 2. 方案设计

### 2.1 将计数保存到任务控制块

系统调用次数属于任务运行期间的状态。不同任务执行相同的系统调用时，需要分别累计。因此，将计数数组作为 `TaskControlBlock` 的字段，与任务状态和任务上下文一起保存。

采用固定长度数组可以直接使用系统调用编号访问计数项，更新和查询均为常数时间操作。当前内核支持的系统调用编号为 `64`、`93`、`124`、`169` 和 `410`，数组长度设置为 `411`，覆盖下标 `0` 至 `410`。

在 RV64 环境中，每个 `usize` 占用 8 字节，因此每个任务新增的计数数组占用 `411 × 8 = 3288` 字节。该方案适合本章任务数量固定、系统调用数量较少的实现。后续扩展系统调用编号时，需要同步调整数组长度，或改用更紧凑的编号映射。

### 2.2 在统一入口计数

计数逻辑放在 `syscall()` 的分发操作之前。这样，每次用户态系统调用进入内核时，首先更新当前任务的计数，再执行对应处理函数。

这一顺序有两个作用：

- `sys_trace` 查询时能够看到包含本次调用的统计结果。
- `sys_yield` 和 `sys_exit` 在切换任务或结束任务之前完成计数，调用归属保持正确。

如果将统计放在处理函数返回之后，`sys_yield` 的执行会跨越任务切换，`sys_exit` 则不会正常返回。统一入口的前置统计可以避免这些问题，也使每个处理函数专注于自身功能。

### 2.3 内存访问与计数查询分别处理

请求 `0` 和 `1` 将 `id` 解释为地址，需要转换为裸指针并执行解引用；请求 `2` 将 `id` 解释为系统调用编号，通过任务管理模块查询数组。

这一区分直接决定实现是否正确。例如，查询编号 `169` 的调用次数时，应读取计数数组的第 `169` 项。将 `169` 转换为指针后解引用，会访问低地址内存，无法得到统计结果，还可能触发访问异常。

本章使用直接内存访问方式，读写操作假定用户传入有效地址。裸指针解引用放在 `unsafe` 块中，整数到指针的转换本身不需要 `unsafe`。这一实现尚未提供完整的用户地址验证；引入地址空间隔离后，需要结合页表和访问权限检查实现用户内存访问。

## 3. 文件修改与实现

### 3.1 `os/src/task/task.rs`：扩展任务控制块

新增统计范围常量和计数字段：

```rust
pub const SYSCALL_COUNT: usize = 411;

pub struct TaskControlBlock {
    pub task_status: TaskStatus,
    pub task_cx: TaskContext,
    pub syscall_counts: [usize; SYSCALL_COUNT],
}
```

`syscall_counts[id]` 表示该任务调用编号为 `id` 的系统调用的次数。任务切换时，数组继续保存在对应任务控制块中，恢复执行后可以继续累计。任务之间各自拥有数组，其他任务的输出、时间查询和主动调度不会改变当前任务的统计结果。

### 3.2 `os/src/task/mod.rs`：初始化与访问统计数据

在 `TASK_MANAGER` 初始化任务数组时，为新增字段设置初值：

```rust
syscall_counts: [0; task::SYSCALL_COUNT],
```

所有任务的计数从零开始，并沿用现有任务控制块的初始化流程。

随后新增 `record_syscall()` 和 `syscall_count()`：

```rust
pub fn record_syscall(id: usize) {
    let mut inner = TASK_MANAGER.inner.exclusive_access();
    let current = inner.current_task;
    if let Some(count) = inner.tasks[current].syscall_counts.get_mut(id) {
        *count += 1;
    }
}

pub fn syscall_count(id: usize) -> usize {
    let inner = TASK_MANAGER.inner.exclusive_access();
    inner.tasks[inner.current_task]
        .syscall_counts
        .get(id)
        .copied()
        .unwrap_or(0)
}
```

两个接口均通过 `current_task` 定位正在运行的任务，并使用现有的 `UPSafeCell::exclusive_access()` 取得任务管理器内部数据的访问权。这沿用了本章单核内核的内部可变性管理方式。

更新接口使用 `get_mut()`，查询接口使用 `get()`，避免数组下标越界。对于超出统计范围的编号，更新接口跳过记录，查询接口返回 `0`。系统调用入口对不支持的实际调用仍保留原有的异常处理方式。

这些函数只进行短暂的数据访问，返回时释放借用，不在持有任务管理器内部借用的情况下执行任务切换。

### 3.3 `os/src/syscall/mod.rs`：接入统一计数

在 `syscall()` 的 `match` 之前增加：

```rust
crate::task::record_syscall(syscall_id);
```

原有的系统调用编号和分发分支保持不变。用户态执行 `ecall` 后，陷阱处理器将编号和参数交给 `syscall()`，入口先记录次数，再调用 `sys_write`、`sys_yield`、`sys_get_time` 或 `sys_trace` 等处理函数。

以官方 trace 测例的前两次查询为例：

| 操作 | 本次进入内核后 `sys_trace` 的累计次数 | 查询结果 |
| --- | --- | --- |
| `count_syscall(169)` | `1` | 当前任务的时间查询次数 |
| `count_syscall(410)` | `2` | `2` |

第二次查询返回 `2`，说明查询本身已经计入。该行为与测例中的 `assert_eq!(2, count_syscall(SYSCALL_TRACE))` 一致。

### 3.4 `os/src/syscall/process.rs`：完成 `sys_trace`

保留函数接口，通过 `match` 实现请求分发：

```rust
match _trace_request {
    0 => {
        let id = _id as *const u8;
        unsafe { *id as isize }
    }
    1 => {
        let id = _id as *mut u8;
        unsafe { *id = _data as u8 };
        0
    }
    2 => crate::task::syscall_count(_id) as isize,
    _ => -1,
}
```

读取分支使用 `*const u8`，将读取到的字节扩展为 `isize` 返回。写入分支使用 `*mut u8`，通过 `_data as u8` 保留最低 8 位，例如传入 `0x1234` 时实际写入 `0x34`。计数分支调用任务管理接口，非法请求返回 `-1`。

实现过程中还修正了原始代码中的括号和指针赋值语法，并补充公开函数的文档注释，以满足内核的编译检查要求。

`sys_get_time` 沿用原有实现：通过 `get_time_us()` 获取时间，将其拆分为 `TimeVal` 中的秒和微秒字段，并写入用户提供的位置。该功能在本次修改前已经存在，本次通过 sleep 测例进行回归验证。

## 4. 运行环境兼容性处理

### 4.1 超时问题的定位

最初在 Docker 中运行测试时，用户程序和内核均编译成功，QEMU 输出 RustSBI 初始化日志后停止推进，30 秒后被 `timeout` 终止，返回 `124`。检查器未找到任何第三章预期输出，结果为 `0/7`。

为确定停滞位置，使用 QEMU 的 `-d int` 异常日志记录功能采集启动轨迹。首个异常为：

```text
cause=2, epc=0x8001349e, desc=illegal_instruction
```

该地址位于 RustSBI 固件区域。检查对应指令后，确认它读取 `mcountinhibit` CSR。随后日志反复出现地址 `0` 的取指异常，说明故障发生在固件交接阶段，内核尚未正常开始执行。

当前容器原先使用 QEMU `7.0.0`。在相同固件和内核条件下升级到 `8.2.10` 后，固件成功输出跳转到 `0x80200000` 的日志，随后出现 `[kernel] Hello, world!`，启动超时得到解决。

### 4.2 `os/src/sbi.rs`：适配现代 SBI 扩展

仓库使用 RustSBI `0.4.1`，内核中的输出和定时器接口原先仍采用旧版 SBI 编号。本次将调用封装调整为扩展编号与功能编号分离的形式：

| 功能 | 扩展编号，放入 `a7` | 功能编号，放入 `a6` |
| --- | --- | --- |
| 设置定时器 | TIME：`0x54494D45` | `0` |
| 输出一个字节 | DBCN：`0x4442434E` | `2` |
| 系统关机 | System Reset：`0x53525354` | `0` |

通用封装将 `a0` 和 `a1` 声明为 `inlateout` 寄存器，分别接收错误码和返回值。这样，编译器能够正确识别 `ecall` 对返回寄存器的修改。原有的 System Reset 关机接口复用新封装，保持关机类型和原因参数为零。

这一修改使内核输出和定时器调用适配当前固件。仅完成 SBI 接口修改时，旧 QEMU 的固件异常仍然存在；接口适配与模拟器升级共同构成了本次可运行环境。

### 4.3 `Dockerfile` 与 `README.md`：固定运行环境

`Dockerfile` 将 `QEMU_VERSION` 更新为 `8.2.10`，构建目录改为引用该变量，并增加新版构建流程需要的 Python 虚拟环境和包管理依赖。配置参数增加 `--disable-docs`，减少文档构建依赖。

`README.md` 补充 QEMU 与固件的兼容性说明，以及旧镜像的更新方式。将版本固定到 Dockerfile 后，后续创建镜像能够复现相同环境，避免只在某个运行中的容器里保留修复。

本次实际验证是在已有容器中编译安装 QEMU `8.2.10` 后完成的；Dockerfile 的完整镜像重建尚未单独验证。

## 5. 测试与结果

### 5.1 验证方法

先在 `os` 目录执行编译检查：

```sh
cargo check --release
```

编译通过后，在 Docker 的 `/mnt` 目录运行第三章检查器：

```sh
make -C ci-user test CHAPTER=3
```

检查器构建用户测例与内核，启动 QEMU，再根据运行输出进行匹配。测试期间使用临时替换的构建文件，结束时恢复原始文件。

### 5.2 功能验证

| 测例 | 验证内容 | 结果 |
| --- | --- | --- |
| `ch3_sleep` | 时间查询返回有效值，循环让出 CPU 后达到等待时间 | 通过 |
| `ch3_sleep1` | `sleep(100)` 完成后输出起止时间和时间差 | 通过 |
| `ch3_trace` | 时间、trace、write、yield 和 exit 的任务级调用统计，以及单字节读写 | 通过 |

trace 测例先后检查 trace 次数为 `2` 和 `7`，并确认尚未执行输出时 write 次数为 `0`，输出后为 `2`。测例还读取初始值为 `111` 的局部变量，通过追踪接口改写该变量，并使用 `read_volatile` 验证写入结果。

运行日志包含以下关键输出，检查器添加的随机后缀在此省略：

```text
[kernel] Hello, world!
get_time OK!
Test sleep1 passed!
string from task trace test
Test trace OK!
Test sleep OK!
Test passed: 7/7
```

上述结果表明，内核完成了固件交接，第三章七项输出检查全部通过，trace 测例中的断言也执行成功。任务结束后的 `All applications completed!` 来自本章既有的结束路径，随后 panic handler 调用关机接口，QEMU 正常退出。

首次通过功能测试时，仓库尚未创建 `reports/lab1.md`，命令在 `7/7` 后因缺少报告返回失败。本报告加入规定路径后，再次执行完整评测，得到：

```text
Test passed13853: 7/7
Report for lab1 found.
```

该次运行的 `sleep(100)` 起始时间为 `80ms`，结束时间为 `181ms`，输出时间差为 `101ms`。最终命令退出码为 `0`，功能检查和报告文件存在性检查均通过。报告检查只确认规定路径下的文件存在，报告内容依据本次实际实现和测试记录整理。

## 6. 实验总结

本实验在现有多任务内核中增加了任务级追踪能力。计数数组保存在任务控制块内，统计入口位于系统调用分发之前，`sys_trace` 根据请求类型完成字节读写或计数查询。这一组织方式使调用次数与任务生命周期保持一致，并满足查询本次调用也计入统计的要求。

调试过程中，异常轨迹将启动故障定位到 RustSBI 固件，QEMU 升级后的对照运行验证了环境兼容性修复。内核功能与运行环境分别完成修改后，第三章七项检查全部通过。

当前实现的适用范围仍以本章为限：字节访问假定地址有效，计数数组覆盖已有系统调用编号，时间参数沿用仓库配置。后续增加地址空间隔离、新系统调用或不同硬件平台时，需要相应完善用户地址检查、统计范围和时钟参数。
